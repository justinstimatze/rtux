## a. Swap tiering: zram writeback vs zswap

### What the sources say

1. **The failure has a name: LRU inversion, and it is documented for exactly this layout.** Chris Down (Meta kernel/cgroup engineer) writes that with zram at higher priority "the kernel prefers zram for all allocations. When zram fills up, it switches to the disk based swap for all future allocations", so zram fills with whatever was swapped out first, which "is usually completely inversely correlated with the pages that you actually need now", while newer, hotter pages "are forced to spill over to the lower-priority device". His advice: "Do not run zram alongside disk swap wherever possible." (https://chrisdown.name/2026/03/24/zswap-vs-zram-when-to-use-what.html, read as `down-zswap.fold`). So yes, zram plus a lower-priority disk swapfile is a documented anti-pattern per the cgroup-memory maintainer's own write-up. It is one author's opinion, not a kernel doc; the kernel docs say nothing against it.

2. **zswap is the in-kernel fix.** Kernel doc: zswap "evicts pages from compressed cache on an LRU basis to the backing swap device when the compressed pool reaches its size limit" (https://docs.kernel.org/admin-guide/mm/zswap.html; read from raw `Documentation/admin-guide/mm/zswap.rst`). It has an optional shrinker: "When there is a sizable amount of cold memory residing in the zswap pool, it can be advantageous to proactively write these cold pages to swap... By default, the zswap shrinker is disabled" (`zswap.shrinker_enabled`). On this host the Ubuntu kernel builds `CONFIG_ZSWAP_SHRINKER_DEFAULT_ON=y` and the live value is `Y`. zswap also has hysteresis: `accept_threshold_percent` refuses new pages "until it has sufficient space" after hitting the limit, to avoid "flipping pages in and out zswap pool" (same doc). Down describes the dynamic shrinker as driven by live feedback (swap-in rates and compression ratios) rather than static thresholds.

3. **zswap has a cliff of its own.** When the pool is at its limit, the incoming page is rejected and, with writeback enabled (default), goes straight to disk (Down, same article). Per-cgroup `memory.zswap.writeback=0` disables all device swapping for that cgroup, "both zswap writebacks, and swapping due to zswap store failures", with the caveat of reclaim inefficiency when stores keep failing (cgroup-v2 doc: https://docs.kernel.org/admin-guide/cgroup-v2.html, read as `cgroup-v2.rst`; also `memory.zswap.max`, `memory.zswap.current`).

4. **zram writeback is a manual workaround.** Kernel doc (https://docs.kernel.org/admin-guide/blockdev/zram.html, read as `zram.rst`): `backing_dev` must be set before disksize ("It supports only partitions at this moment"), `echo idle > writeback`, `huge`, `huge_idle`, `incompressible`, `idle` marking by age (`echo 86400 > idle`), and `writeback_limit` for a wear budget. Nothing triggers it automatically. Down: "zram does not write out pages to it automatically, and the kernel has no internal heuristic to decide when to move data"; it needs a timer, takes a snapshot, and "if memory pressure suddenly rises, it may be too late to run your script". He calls it "a workaround, not a solution". Also: it needs a dedicated unformatted block device, so the existing /swapfile cannot be the backing store. The 980M LVM partition could, but it is tiny.

5. **What distros and vendors ship** (each is a read page):
   - Fedora: swap-on-zram, size 50% of RAM capped at 4 GiB, higher swap priority, and "Do not create swap partition/LV with default installations". The same page says that if the user adds drive swap there will be two swaps with zram at higher priority, and it explains "Why not zswap?" (zswap needs disk swap; eviction to disk can leak user data). No writeback device by default. https://fedoraproject.org/wiki/Changes/SwapOnZRAM
   - Ubuntu: this host's kernel has zswap compiled in but off; default desktop swap is a swapfile. An Ubuntu discourse thread on 26.04 has Ubuntu engineers arguing for zswap over zram where disk swap exists ("zram should not be in the picture", "zswap is generally superior, and zram should be considered only if you don't have any appropriate backing store") but that is discussion, not a shipped default. https://discourse.ubuntu.com/t/will-zram-be-enabled-by-default-in-26-04/73070 (read via `.json`)
   - Android: zram only. AOSP's mmd treats writeback as an optional post-processing stage: recompress first, then "If memory pressure continues and pages reach writeback idle age (typically 20 hours or more), mmd triggers writeback" to a loop device on flash, default off (`mmd.zram.writeback.enabled`), with a daily write budget (`mmd.zram.writeback.limit.enabled`). https://source.android.com/docs/core/perf/mmd
   - ChromeOS: zram only, no disk swap. The upstart `swap.conf` I read sizes zram at 1.5x RAM (1x on ARM); the 2011 design doc says Chromebooks "do not use swap" and chose userspace tab discarding. Those are old snapshots (commit b73e97e of platform/init and a 2011 doc), not current behavior. https://chromium.googlesource.com/chromiumos/platform/init/+/b73e97e842f5ff70e0e6d53d6008e187fe24cdbb/swap.conf and https://www.chromium.org/chromium-os/chromiumos-design-docs/out-of-memory-handling
   - Nobody in this set ships "zram at priority 100 plus a big lower-priority disk swapfile, with no writeback automation" as a managed design. Mixed configs are user-assembled.

### Implication for rtux

- **The tier layout is the root of causes 1 and 3, and it is a host decision, not daemon code.** Two coherent fixes:
  - **A (cheapest, interim):** `swapoff` /swapfile and dm-2, keep zram only. Then "swap fraction" really means zram fullness, so the existing 0.70/0.85 gates become meaningful, and rtux's `memory.reclaim` can only ever land in compressed RAM. Cost: no disk safety net; when zram fills, anon cannot be evicted and the kernel/oomd/rtux kill must act (Down says pair zram with a userspace killer).
  - **B (what the sources recommend):** disable zram swap, `zswap.enabled=1` with `zstd`, `max_pool_percent` raised from the 20 default, `shrinker_enabled=Y` (already), keep /swapfile as the backing tier. Cold pages drain to disk by LRU, hot pages stay compressed. This removes inversion by construction. Cost: pool-full cliff to disk; and unlike zram, zswap memory is charged to cgroups (`memory.zswap.current`).
- **zram writeback is not recommended** for this host: needs a dedicated partition, time-based idle marking, manual timer. If a daemon has to own tiering, rtux could drive `idle`/`writeback` itself, but that is building the thing zswap already is (violates the repo's adopt-before-build rule).
- **Under B, rtux gets a precise per-cgroup control:** write `memory.zswap.writeback=0` on a scope before rtux's forced `memory.reclaim`, restore it on thaw. That makes "hibernate to compressed RAM" true by construction for that scope, without the gate having to read `/proc/swaps`. Caveat from the docs: recurring store failures (incompressible pages) cause reclaim inefficiency, so cap the reclaim amount (see d).

## b. How mature killers decide to kill

| Tool | Swap handling | IO pressure | Source |
|---|---|---|---|
| systemd-oomd | System-wide `swap_used / swap_total` vs `SwapUsedLimit` (commented default 90%), combined with "memory available below the same fraction". Per-unit memory PSI uses `avg10` over a duration (defaults 60% for 30 s). No tier awareness. Its man page says swap is "highly recommended" so oomd has time to react. | None. Only memory PSI. | `oomd-manager.c` (lines ~477-479), `oomd-conf` (`#SwapUsedLimit=90%`, `#DefaultMemoryPressureLimit=60%`, `#DefaultMemoryPressureDurationSec=30s`), https://github.com/systemd/systemd/tree/main/src/oom |
| Meta oomd | Plugin `swap_free` has two args: `threshold_pct` and `swapout_bps_threshold`: "CONTINUE if the percentage of free swap is below `threshold_pct` and the current swap-out rate is at least `swapout_bps_threshold`". Also `swap_above_memory_max`. | Android lmkd | `swap_free_low_percentage` (default 10). Crucially its free-swap is made ZRAM-aware: `get_free_swap` returns `min(free_swap, easy_available * swap_compression_ratio)`; the code comment says that with ZRAM "free_swap can't be used directly because swap space is taken from the free memory or reclaimed". `swap_util_max` kills when swapped anon / swappable anon exceeds a percent while below the high watermark. Key findings:
- **Only two tools combine swap level with swap rate or RAM cost:** Meta oomd (`swapout_bps_threshold`) and nohang (zram RAM-used). lmkd adjusts for zram being RAM. **None of them models "fast tier full, slow tier in use".** systemd-oomd and earlyoom have the exact same blind spot as rtux's `swap_used_fraction`. So the post-mortem's cause 1 is not an rtux quirk; copying systemd-oomd would not fix it. The best precedent is Meta oomd's pairing of a level with a swap-out rate.
- **The only mature "thrashing means kill" signal is lmkd's file-refault percentage**, which matches this incident (compositor file refaults). lmkd also protects the foreground: it applies `min_score_adj` so perceptible/foreground apps are not killed unless the watermark is below min or thrashing is at critical levels.
- **IO pressure:** Meta oomd supports it natively. TMO (below) says memory PSI alone is "insufficient" and Senpai watches IO PSI too.
- **Kernel PSI triggers** (poll on `/proc/pressure/{memory,io}` with `<some|full> <stall_us> <window_us>`, e.g. "full 50000 1000000") avoid avg10 lag; documented at https://docs.kernel.org/accounting/psi.html (read). lmkd uses them with a 1000 ms window and 70 ms partial/700 ms complete stall defaults.

### Implication for rtux

- Replace the swap gate with a tier-aware one (see Ranking #1). Use two inputs, in the Meta oomd shape: *disk-swap used above a small floor* AND *swap-out rate (pswpout, or per-device write bytes) above X*, OR (zram full AND disk swap growing). For a zram-only layout (fix A) the existing fraction is correct.
- Add a lmkd-style thrashing signal: delta of `workingset_refault_file` (system `/proc/vmstat`, and per-cgroup `memory.stat` of the compositor; both fields documented in cgroup-v2.rst) divided by file LRU size, with decay and a reset after each kill.
- Add IO PSI `full` (system) as an escalation input and use PSI triggers rather than avg10 sampling where possible.
- Borrow `pressure_rising_beyond`'s "10 s not falling rapidly" idea only as a guard against killing when pressure is already collapsing; do not use it to stand down while the spine is still faulting.

## c. Protecting interactive file pages

### What the sources say

1. **`memory.min`/`memory.low` semantics** (cgroup-v2.rst, https://docs.kernel.org/admin-guide/cgroup-v2.html): `memory.min` is hard: usage within it "won't be reclaimed under any conditions", and OOM killer is invoked if there is no unprotected reclaimable memory. `memory.low` is best-effort. Effective protection is capped by ancestors' values; `memory_recursiveprot` mount option applies protection to whole subtrees. Protection "applies relatively to the target of the reclaim (i.e. any of memory cgroup limits, proactive memory.reclaim or global reclaim...)".
2. **Charging of shared library page cache:** "A memory area is charged to the cgroup which instantiated it and stays charged to the cgroup until the area is released"; for areas used by several cgroups "To which cgroup the area will be charged is in-deterministic" (same doc, "Memory Ownership"). Only anon+file pages charged to the compositor's own cgroup are covered by its 512M `memory.min`.
3. **MGLRU `min_ttl_ms`** (https://docs.kernel.org/admin-guide/mm/multigen_lru.html, read as `mglru.rst`): "Users can write N to min_ttl_ms to prevent the working set of N milliseconds from getting evicted. The OOM killer is triggered if this working set cannot be kept in memory." and "N=1000 usually eliminates intolerable janks due to thrashing. Larger values like N=3000 make janks less noticeable at the risk of premature OOM kills." The source (`mm/vmscan.c`, `lru_gen_age_node`, read) shows the mechanism: the OOM killer is invoked from kswapd aging only if every memcg's oldest generation is younger than `min_ttl`, and memcgs below `memory.min` or too small count as not reclaimable (so they do not by themselves keep the check from firing). Default is 0, which is live on this host.
4. **le9 / `clean_low_kbytes` / `anon_min_kbytes`** are out-of-tree patches (https://github.com/hakavlad/le9-patch README, read). The README states these knobs "have no effect when mg-LRU is enabled". On this host MGLRU is enabled and `/proc/sys/vm` has none of the knobs, so they are unavailable; ChromeOS/CachyOS-style kernels are the only places they exist. Last push 2023.
5. **mlock of the compositor:** I found no primary source I could fetch (the prelockd README URL 404'd). UNSOURCED: mlocking would pin the compositor anon and mapped pages but the large shared libraries/shaders it maps are the issue, and mlock needs RLIMIT_MEMLOCK headroom. I do not recommend it over cgroup protection.
6. **TMO's kernel change** (ASPLOS'22, https://www.pdl.cmu.edu/ftp/NVM/tmo_asplos22.pdf, read as `tmo2.txt`): Meta changed reclaim to take file cache only "so long as no refaults occur", then balance file against swap by refault rate and swap-in rate; they report this is upstreamed. This is the kernel-side defense that keeps working-set file pages from being evicted ahead of cold anon.

### Implication for rtux

- **Host/cgroup config, check first:** the compositor's `memory.min=512M` protects only pages charged to its cgroup. If libs and shaders were first loaded by another cgroup (INFERRED, plausible given the charging rule), the faults will not be covered. Measure before changing: compare `workingset_refault_file` and `pgmajfault` in `memory.stat` of the compositor vs its ancestors (`user@1000.service`, `session.slice`), and set `memory.low` on the ancestor that owns the shared libs, with `memory_recursiveprot`. Make sure rtux's *victim* scopes have `memory.low=0` so protection does not skew their forced reclaim.
- **`lru_gen/min_ttl_ms=1000`** is the only kernel thrash-prevention knob available here. It converts "minutes of file thrash" into a kernel OOM kill, so it needs a plan for who the victim is (oom_score_adj of background Claude/ollama scopes high, compositor low; UNSOURCED, verify). Treat as an experiment with oomd/rtux still in front of it.
- Do not plan on le9 or `clean_low_kbytes`.

## d. Proactive reclaim and freeze/thaw policy

### What the sources say

1. **Senpai/TMO** (TMO paper, read): per cgroup every ~6 s, `reclaim_mem = current_mem x reclaim_ratio x max(0, 1 - PSI_some / PSI_threshold)` with `reclaim_ratio=0.0005` and `PSI_threshold=0.1%`; max 1% of workload size per period; "No memory is reclaimed when PSI_some is above PSI_threshold". The 6 s period is "to leave enough time to measure the delayed impact (refaults) of reclaimed memory". They added stateless `memory.reclaim` so a growing workload is not blocked by a limit. Senpai also "has additional mechanisms to modulate reclaim in certain events such as SSD write endurance thresholds being exceeded or swap space exhaustion", and monitors IO PSI because "refaults induced by Senpai might not impact the workload in the form of fault latencies, but might slow down the storage device enough to impact the workload's operation indirectly". Senpai repo README: https://github.com/facebookincubator/senpai.
2. **`memory.reclaim`** doc: the kernel "can over or under reclaim", returns `-EAGAIN` if less was reclaimed; supports `swappiness=` (0-200, `max` = anon only) per call (cgroup-v2.rst). `swappiness=max` is the knob that forces anon-only; a low value biases toward file.
3. **Backoff precedents (none are about thawing):** zswap `accept_threshold_percent` (refuse until the pool drains, to stop in-out flapping); lmkd resets thrashing baselines and decays the counter after each kill; nohang `psi_post_action_delay` (>=10 s) after any action; oomd `pressure_rising_beyond` requires sustained and non-falling pressure. I found **no primary source on freeze/thaw hysteresis for cgroup.freeze** in oomd, lmkd, systemd or the kernel docs. The cgroup doc only specifies that freeze stops tasks and fatal signals still work. Treat the thaw policy as rtux's own design.
4. **Android mmd** (above) shows the same shape for cold-page eviction: staged (recompress, then writeback at 20 h idle age), only while the device is idle, with a daily write budget.

### Implication for rtux

- Forced per-scope `memory.reclaim` of the whole scope is the opposite of Senpai: it is large, not feedback-scaled, and ignores IO PSI. Cap each call (a fraction of scope size, with the -EAGAIN result as feedback), skip it whenever the tier gate says disk is in play (or set `memory.zswap.writeback=0` under fix B), and stop it when IO PSI is already high, since reclaim output is itself IO.
- Thaw hysteresis: make the calm window per scope and growing (e.g. 10 s, then 60 s, then minutes on each re-freeze in the same episode), require IO PSI and the spine fault rate quiet (not only memory PSI), and thaw one scope at a time so the working-set fault-back is not simultaneous. Escalate a scope re-frozen more than N times to kill. These specifics are rtux design (UNSOURCED); the sources support the principles (measure delayed effects before the next action, back off after actions, protect the storage device).
- A frozen scope that is not reclaimed frees nothing; a reclaimed one costs IO twice (write now, fault-back later). With the tier fix the first cost is RAM-only; without it, freeze+reclaim+thaw is a net IO generator, which is what the post-mortem measured (9.4 GB in 22 min).

## Ranking of changes for rtux

1. **[daemon] Tier-aware swap gate for kill and reclaim.** Use per-device `/proc/swaps` (zram full, disk swap used above a floor) plus a swap-out/disk-write rate, Meta oomd `swap_free`+`swapout_bps` shape; this is the one place every mature killer is blind, so there is no off-the-shelf answer.
2. **[HOST CONFIG: swap layout] Remove the inversion.** Interim A: swapoff /swapfile and dm-2 so swap == zram. Target B: disable zram swap, enable zswap (zstd, larger pool, shrinker on) over /swapfile. The only sourced cure for LRU inversion; rtux cannot fix it from userspace.
3. **[daemon] Escalate on file-refault thrash and IO PSI full.** lmkd's `workingset_refault_file / file_lru` thrashing percentage plus IO PSI `full` (PSI triggers) drive Critical, and block thaw while the compositor's fault rate is high.
4. **[daemon] Bound and gate forced reclaim.** Senpai-style capped, feedback-driven `memory.reclaim` (swappiness arg, -EAGAIN), skipped when IO PSI is high or the tier gate trips.
5. **[daemon] Per-scope growing thaw backoff, staggered thaws, re-freeze count escalates to kill.** Stops the ping-pong; design is rtux's own since no source covers cgroup.freeze hysteresis.
6. **[daemon, needs zswap] Use `memory.zswap.writeback=0` on victim scopes during forced reclaim.** Makes RAM-only hibernation true per cgroup; only after #2B.
7. **[HOST CONFIG: cgroup] Move `memory.low`/`memory.min` to the cgroup that actually owns the shared libs/shaders** (after measuring per-cgroup refaults), with `memory_recursiveprot`. Charging-to-instantiator rule means 512M on the compositor may protect little of what it faults.
8. **[HOST CONFIG: sysctl-ish] `lru_gen/min_ttl_ms=1000` experiment**, after deciding who the kernel OOM victim is. Kernel doc recommends it for desktops; it turns thrash into a kill.
9. **Drop:** le9/`clean_low_kbytes`/`anon_min_kbytes` (unavailable, no-op under MGLRU), zram writeback (manual, needs a dedicated partition), mlock of the compositor (no source).
